# AIに説明させる

AIに作業を任せると、承認を求められる回数が増えます。差分を読んで判断するのは重く、読まずに OK すると承認に意味がなくなります。このページは、その間を埋めるための決まりです。**差分を読まなくても、説明と、説明が指す数か所を見れば判断できる**ことを目指します。

## 説明の大きさと形式

| 場面 | 形式 | 頻度 |
| --- | --- | --- |
| 1つの変更（プルリクエスト・作業の報告）の承認 | One-pager の[変更の説明](./changes.md) | 変更のたび |
| 方針・構成・比較の相談 | One-pager の概念・アーキテクチャ・比較の型 | 判断が要るとき |
| まとまった作業の報告・提案 | Marp（PDF） | 節目ごと |
| プロジェクト全体の構成・使い方・判断・計画 | Docusaurus（このサイトのような形） | 育て続ける |

小さいほうから使います。1枚に収まらない変更は、変更を分けるか、Marp か Docusaurus の1ページにします。

## 変更の説明に書かせること

One-pager の `examples/change.html` が型です。

| 節 | 書くこと | 読み手が確かめること |
| --- | --- | --- |
| 見出しと要約 | 変更名と、マージすると何ができるようになるか、何が変わらないか | 頼んだことと合っているか |
| 何が変わるか | 今・マージ後・戻すとき | 戻し方が書いてあるか |
| 確かめたこと・確かめていないこと | 確かめたことは、どう確かめたか（件数・比較の方法）まで | 確かめていないことが空でないか。空なら疑う |
| 判断のために見るところ | 読み手が自分で見て答えられる問いを3つ | コードを読まないと答えられない問いが無いか |
| 決めてほしいこと | 1つだけ、推奨と一緒に | 推奨の理由が上の節から読み取れるか |

右の列が満たされない説明は、**差し戻してよい説明**です。中身を全部見なくても、説明の形が崩れていることは見て分かります。

## プロジェクトの指示に書いておく文

AIへの指示ファイル（`CLAUDE.md` など）に次を貼ると、説明の形が揃います。One-pager を取り込んだ場所に合わせてパスを直します。

```markdown
## 説明のしかた

- 変更の承認を求めるときは、「変更の説明」を1枚作り、PNGにして見せる。
  - 型は `tools/one-pager/examples/change.html`
  - `node tools/one-pager/scripts/check.mjs <ファイル>` を通す
- 確かめたことには、どう確かめたかを書く。
- 確かめていないことを必ず書く。推測を確認済みに混ぜない。
- 「判断のために見るところ」は、コードを読まずに答えられる問いにする。
  （画面、ファイルの数行、数値）
- 決めてほしいことは1つだけ、推奨と一緒に書く。無ければ「マージしてよい」と書く。
- 1枚に収まらない変更は分ける。
- プロジェクト全体に関わる説明は Docusaurus のサイトに書き足す。
```

## まだ分かっていないこと

この決まりは docs-toolkit 自身の変更で試し始めたところです（[変更の説明](./changes.md)）。実際の承認が速く・確かになるかは、何回か使ってから見直します（[ロードマップ](./roadmap.md)の優先1）。
