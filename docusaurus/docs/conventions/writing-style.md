description: 読み手が判断・作業できる技術文書を書くための基本ルールです。
---

## 基本原則

- 結論、判断、完了条件を先に書きます。
- 一つの段落では一つの論点を扱います。
- 事実、判断、仮定、未決事項を区別します。
- 表は比較と検索に使い、長い説明文の箱として使いません。
- 手順は作業者が実行する順に並べ、操作と期待結果を分けます。
- 「適切に」「必要に応じて」など、判断基準が不明な表現を避けます。

## 見出し

見出しは内容を予測できる名詞句または短い問いにします。階層はページタイトル、`##`、`###`までを基本とします。

良い例:

- スコープ
- エラー処理
- 切り戻し条件
- なぜこの方式を採用したか

避けたい例:

- はじめに
- その他
- 補足事項

## 注記

注記は目的に応じて使い分けます。基本原則の「事実、判断、仮定、未決事項を区別する」に対応する専用の注記型（`decision` / `pending` / `assumption`）があります。

:::note[補足]
本文の理解を助ける情報に使用します。
:::

:::info[参照]
参照先や背景情報に使用します。
:::

:::decision
採用した方式、方針、理由に使用します（`:::decision`）。タイトルは`[採用]`のように置き換えられます。
:::

:::pending
未決事項に使用します（`:::pending`）。決まっていないこと、決める期限、決める人を書きます。
:::

:::assumption
前提や仮定に使用します（`:::assumption`）。崩れた場合に影響が出る条件を明示します。
:::

:::warning[注意]
見落とすと失敗、手戻り、サービス影響につながる情報に使用します。
:::

:::danger[重大]
データ損失、情報漏えい、長時間停止につながる操作や状態に限定します。
:::

## 表

表は行ごとに同じ属性を比較できる場合に使用します。列数が増えすぎる場合や、各セルが複数段落になる場合は、項目ごとの小見出しへ分けます。

| ID | 内容 | 担当 | 期限 |
| --- | --- | --- | --- |
| TBD-001 | 監査ログの保存期間を決める | Security | 2026-08-31 |

## コードとコマンド

コードブロックには言語名を付け、実行場所と期待結果を本文で説明します。プロンプト記号はコピーを妨げるため含めません。

```yaml
auth:
  issuer: "https://id.example.com"
  audience: "example-api"
```

## チェックリスト

チェックリストは、開始条件、完了条件、レビュー観点に使用します。説明が必要な場合は、チェック項目の後に根拠を続けます。

- [ ] オーナーが決まっている
- [ ] 失敗時の挙動が説明されている
- [ ] 監視とログの確認方法がある
- [ ] 切り戻し条件が明確である
