## 最初に決めること

小さな開発変更では、**目的を決めるBrief、途中の判断を求めるチェックポイント、結果を確かめる検証・受け入れ記録**の3つの役割を使います。3ファイルの作成や一律の承認工程は求めません。読み手が必要な情報へ一度で辿れる形を選びます。

| 状況 | 置き方 |
| --- | --- |
| 目的、途中の判断、結果が短く、同じ読み手が確認する | 同じMarkdownへ3つの見出しで統合する |
| Issueに目的と受け入れ条件があり、PRから確認物と結果へ辿れる | BriefはIssue、チェックポイントと検証記録はPRで代替する |
| 判断が不要な小さな修正で、既存条件を既存テストだけで確かめられる | 独立したBriefとチェックポイントを省略し、PRへ対象・方法・結果・証拠を残す |
| 判断者、確認する時点、共有範囲が異なる、または文書が長くなる | 必要な役割だけ別ファイルにし、同じ情報を転記せずリンクする |

配置先、文書名、担当、承認方法は利用プロジェクトが選びます。初回のmacOSローカルPoCは記入例の条件であり、他の利用環境を制限しません。比較や生ログは参照先へ分け、判断に必要な結論と証拠へのリンクだけを本文に置きます。

雛形は見出し、表、箇条書き、リンクだけで読める通常のMarkdownです。必要な項目だけコピーして、山括弧の記入欄を置き換え、不要な章を削除します。形式固有のfront matter、DocMeta、注記や独自CSSは必須ではありません。状態は実際のレビュー状況に合わせ、未決、未実施、未検証、人間の承認待ちを成功・採用・承認済みに変更しません。

リポジトリの [`examples/phase0/review.md`](https://github.com/forsteri/docs-toolkit/blob/codex/issue-2-minimal-templates/examples/phase0/review.md) に、同じ導入PoCの3つの役割を1ファイルにまとめた記入例があります。リンクは今回の提案ブランチ版です。PRで確認する場合は、そのPRのファイル一覧から同じパスを開きます。これはサンプルプロジェクトによる試行であり、実案件での有用性や人間の採用判断を示すものではありません。

## Brief：目的と到達点

**いつ使うか:** 新しい変更を始めるとき、目的、範囲、完了根拠を読み手と揃える必要がある場合に使います。

**省略できる場合:** 既存Issueや依頼文に下記の内容が揃っていれば、それを正本としてリンクします。内容が足りない場合は、足りない項目だけ補います。

**入力:** 依頼、現状を示す資料、既知の制約、既存の受け入れ条件。分からない項目を推測で埋めず、未確定事項へ残します。

### 雛形

```markdown
# <変更名> — Brief

状態: <作成中 / レビュー待ちなど実態>
正本・関連: <Issue、依頼、既存仕様へのリンク>

## 課題と目的

現状: <何に困っているか。根拠へのリンク>
目的: <誰が、何をできるようになるか>

## 対象・対象外

対象: <今回変更・検証する範囲>
対象外: <次の判断まで進めない範囲>
前提・制約: <環境、扱うデータ、変更できる範囲>

## 受け入れ条件

| 条件 | 確認方法・証拠の置き場 |
| --- | --- |
| <読み手が確かめられる到達点> | <操作、テスト、成果物へのリンク> |

## 未確定事項

- <未決事項、影響、何が分かれば決められるか>
- 判断不要なら「なし」。担当や期日は実際に決まっている場合だけ記す。
```

### レビュー観点

- [ ] 課題と目的がつながり、対象外と停止地点を読める。
- [ ] 受け入れ条件に確認方法があり、実装作業の列挙だけになっていない。
- [ ] 前提、確定した要求、未決事項を区別できる。
- [ ] 正本が別にある情報を複製していない。

記入例の「Brief」では、外部原本の生成という目的を、生成物と実行証拠で確認する条件へ結び付けています。

## チェックポイント：次に進むための判断

**いつ使うか:** 途中成果を見て範囲、方式、続行・修正・保留を人間に判断してほしい場合に使います。

**省略できる場合:** 途中の判断や方向修正が不要なら、独立した資料を作らず、PRの確認依頼と検証記録で代替できます。判断が必要なら、PR本文で下記の先頭4項目を満たす形も使えます。

**入力:** Brief、実物へのリンク、現時点の実行結果、未検証事項、次に予定する変更。完成予定の物を「動く物」として記載しません。

### 雛形

```markdown
# <変更名> — チェックポイント

状態: <判断待ち / 修正中など実態>

## 1. 判断してほしいこと

<決めること。選択肢、推奨と理由、選んだ場合の影響>
判断が不要なら「判断依頼なし」とし、確認してほしいことを記す。

## 2. 現状と確認してほしい物

利用者から見た変化: <何ができるようになったか。未動作ならその旨>
確認入口: <実物または原本へのリンク>
確認手順: <何を開き、どの表示・動作を確かめるか>
確認済みの根拠: <検証記録へのリンク。未実施なら明記>

## 3. 未検証・残るリスク

- <未検証の対象、影響、回避策や判断に必要な追加確認>

## 4. 次に進める範囲

判断後に進めること: <具体的な最小範囲>
今回進めないこと: <対象外、別途判断が必要な変更>

## 関連する目的・根拠

- Brief: <リンク>
- 検証・受け入れ記録: <リンク>
```

### レビュー観点

- [ ] 先頭だけで判断依頼、動く物、未検証、次の範囲を把握できる。
- [ ] 推奨案の理由と選択の影響があり、採用済みのように書いていない。
- [ ] 読み手が確認する実物へ辿れ、何を見るかが短く示されている。
- [ ] 作例、作成予定、実際の実行結果を区別できる。

記入例では導入PoCの方式とこの文書の型を続行判断にかけます。サンプルの成功と本採用を分け、Issue #3以降は判断後の予定として示します。

## 検証・受け入れ記録：実施したことと完了根拠

**いつ使うか:** 変更を試した結果を共有するとき、または受け入れを求めるときに使います。失敗や未実施も残します。

**省略できる場合:** 必要な項目を満たすCI実行やPRのテスト結果があるなら、別ファイルを省略できます。生成された説明文や「動いた」という記述だけでは証拠を代替できません。

**入力:** 対象コミットや原本の識別、実行環境、実行コマンドまたは手順、実際の出力、確認した成果物、受け入れ条件。環境差と確認できない事項を含めます。

### 雛形

```markdown
# <変更名> — 検証・受け入れ記録

結論: <確認できた範囲と、残る条件を短く>
人間の受け入れ: <判断待ち、または実際の判断とその記録へのリンク>

## 対象と環境

対象: <コミットSHA、原本の版、取得した共通資産のref>
環境: <OS、実際に使用したツールの版、実行場所>
実施時点: <実際の実施日時、または未実施>
再実行方法: <手順へのリンク、必要な入力>

## 実施結果

| 受け入れ条件・確認項目 | 方法・実行コマンド | 結果 | 証拠 |
| --- | --- | --- | --- |
| <条件> | <手順または参照> | <成功 / 失敗 / 未実施 / 未確認> | <出力、ログ、CI、画像等へのリンク> |

## 未実施・未確認・残る問題

- <環境、表示、失敗ケース、限界とその影響>
- 目視で開いていない出力は「生成成功・目視未確認」と分ける。

## 受け入れ判断

- 実装・機械検査の結果: <確かめられた範囲>
- 人間に残る判断: <採否、実利用、視覚確認など>
- 承認した場合だけ、判断者と判断記録へのリンクを残す。
```

### レビュー観点

- [ ] 対象ref、環境、方法、結果、証拠を対応させて再確認できる。
- [ ] 失敗・未実施・未確認が成功に混ざっていない。
- [ ] HTML生成、ブラウザでの表示確認、内容の妥当性、人間の受け入れを区別できる。
- [ ] 仮の担当、期限、数値、承認を事実として置いていない。

記入例の「検証・受け入れ記録」は、実ログを比較・実験側へ分けて参照します。ここへ同じログや長いファイル一覧を転記しません。

## 統合・代替したときの例

1ファイルへ統合する場合は、先頭にチェックポイント、続けてBrief、検証・受け入れ記録を置くと、判断する読み手が目的と証拠へ辿れます。途中の記録を更新するときは、対象refと検証時点も揃えます。長い経緯はIssue/PRへ分けます。

Issue/PRで代替する場合の短い作例です。以下は記入方法を示す架空の変更で、実施記録ではありません。

```markdown
<!-- Issue本文。Briefの役割を持つ -->
目的: 設定画面で保存した値を再表示できるようにする。
対象: 既存設定の読み書き。対象外: 設定項目の追加。
受け入れ条件: 保存後に再読込して値が一致する。確認結果はPRへ残す。
未決: なし。

<!-- PR本文。チェックポイントと検証記録の役割を持つ -->
判断依頼なし。確認してほしいこと: 保存後の表示とテスト結果。
変化・確認入口: 実際の画面または再現手順へのリンクを記入する。
対象ref・環境: 実際のSHAと環境を記入する。
方法・結果・証拠: 実行後にコマンド、結果、CI等のリンクを記入する。
未実施・残るリスク: 実際の確認範囲に合わせて記入する。
次の範囲: この修正だけを受け入れ対象とする。
```

既存仕様と受け入れ条件が明確な誤記修正などでは、Issueを増やさず、PRへ目的、確認箇所、実施結果、未確認事項をまとめる形でも構いません。文書を省略しても、判断に必要な情報と実施の根拠は省略しません。
