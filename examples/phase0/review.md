# 外部プロジェクトからの文書生成 — Phase 0の記入例

これはdocs-toolkitの導入PoCを題材にした、Brief・チェックポイント・検証記録を1つのMarkdownへまとめる例である。利用対象は公開可能な検証用サンプルであり、実案件での利用実績ではない。実際の実行結果は、証拠が揃った項目だけに記載する。

状態: 技術検証の結果を記録済み。方式・文書の型ともに人間の採用判断前。
正本: [Issue #1](https://github.com/forsteri/docs-toolkit/issues/1)、[Issue #2](https://github.com/forsteri/docs-toolkit/issues/2)、[ROADMAP.md](https://github.com/forsteri/docs-toolkit/blob/f2b5140610377ae80946d999f822cd9ffe1c3343/ROADMAP.md)。

## チェックポイント

### 1. 判断してほしいこと

**別の小さな開発プロジェクトで、Agentに目的・途中成果・確認結果をまとめてもらい、自分はブラウザで読んで続行や修正を返す使い方を試したいか。**

推奨は、この使い方に必要な最小の入口をIssue #3で整えること。目的、途中の判断、最後の確認結果は、まず1つの文書にまとめる。初回にMacへ道具を用意し、文章を直したらHTMLを作り直す手間を引き受ける。道具の置き場や使う版はAgentが記録し、コマンド名やフォルダ名などは実装側で決める。

選択肢は、この範囲で小さく試す、受け入れにくい手間を示して案を見直す、保留。技術方式の細部をすべて理解して選ぶ必要はない。

### 2. 現状と確認してほしい物

現在できるのは、用意済みの検証プロジェクトについて、文書原本と画像からHTMLを作り、実物を読むところまで。任意の案件でAgentへの依頼から準備・生成まで迷わず進められる入口は、まだない。

ブラウザ版の入口では「生成した文書」を開くと、今回実際に作った本文と図を読める。この記入例では、目的・途中の判断・確認結果を1つの文書で受け取る形を確認してほしい。開発中の画面やテスト結果そのものは利用プロジェクト側が用意する。

[使い方と今回の判断](https://github.com/forsteri/docs-toolkit/blob/codex/issue-1-adoption-poc/experiments/phase0-adoption/README.md) に、初回準備、普段の依頼、更新時の分担と、実物を見る順序を示している。[Brief](#brief) と [検証・受け入れ記録](#検証受け入れ記録) は、目的と実際の根拠を確認したいときに参照できる。

### 3. 未検証・残るリスク

- 原本を更新してもHTMLは自動更新されない。読み手へ渡す前に作り直す必要がある。
- 初回の道具の導入からの負担と、実案件で確認が楽になるかは未確認。複数人・複数Macでの管理もまだ試していない。
- 今回確認したのはMacのサンプルと単体HTML。サイト横断検索、他OS・PDF・スライドが最初から必要なら、範囲を見直す必要がある。
- 既存生成スクリプトは画像が欠けても成功と表示する問題があり、今回の試行内だけで回避した。日常利用で欠落を見逃さない入口は、次の実装の対象。
- HTMLの表示はローカルHTTP経由で確認。ファイルの直接表示は自動化の制限で未確認であり、普段の持ち出し方でも確認する必要がある。

### 4. 次に進める範囲

続行の判断後に、Issue #3で1つの利用方式・単体HTMLに絞り、別プロジェクトの原本から生成する入口、資産欠落の診断、原本や出力の上書き防止、外部利用の確認を整える。そこまでで実案件の有用性を確認済みとはしない。

今回はレビュー資料の組み替えまで。Issue #3の実装、実案件への導入、公開は進めない。文書を1ファイルで受け取る形が使いやすいかは、実際の利用で見直す。

## Brief

### 課題と目的

現状: 既存のツールキットには形式別の同梱サンプルとスクリプトがあるが、外部利用の取得方法と原本・資産・生成物の境界は比較・検証が必要である。目的や判断材料の文書の型も、最小セットを試して確認する必要がある。根拠はIssue #1・#2とROADMAP.mdを正本とする。

目的: 初期利用者とコーディングエージェントが、小さな変更の目的を揃え、外部原本から作った実物をレビューし、次の範囲へ進むかを判断できる状態にする。

### 対象・対象外

対象: 4つの取得方式の比較、少なくとも1案の外部利用PoC、再実行方法と検証記録、Brief・チェックポイント・検証記録の雛形と記入例。

対象外: Issue #3以降の本実装、全形式・全OS対応、新しい配信サービスや常駐基盤、実案件やグローバル設定の変更、人間による採用判断の代行。

前提・制約: 第一の対象はmacOSローカル。Markdown中心でブラウザ閲覧を優先する。公開可能なサンプルだけを使い、検証用プロジェクトはツールキットの作業ツリー外へ置く。この条件は今回の試行を定め、将来の全利用条件を固定しない。

- 期限と人間の承認者はこの例で新たに設定しない。未検証の対応環境もサポート対象として約束しない。

### この記入例をブラウザで確認する

このファイルは、雛形の使い方を示す記入例である。以下は、この記入例自身を既存PandocテンプレートでHTMLにする手順であり、外部利用PoCの検証とは区別する。リポジトリ直下から実行する。Pandoc 3.xが必要で、生成物はGit追跡対象外の `output/` へ置く。

```bash
mkdir -p output/phase0
(
  cd pandoc
  pandoc --defaults defaults/html.yaml --fail-if-warnings \
    --metadata title='Phase 0 の記入例' \
    ../examples/phase0/review.md -o ../output/phase0/review.html
)
```

`output/phase0/review.html` をブラウザで開き、チェックポイントの先頭4項目と、Brief・実行証拠への参照を確認する。リンク先のMarkdownは原本を示しており、単体HTMLと一緒に資料一式を持ち出すための配布処理は、この例には含めない。
