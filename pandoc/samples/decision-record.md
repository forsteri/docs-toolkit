# 決定

Webアプリケーションの利用者認証には、OAuth 2.0 Authorization Code FlowとPKCEを使用します。アクセストークンをブラウザの永続ストレージへ保存せず、バックエンドセッションを介して利用します。

::: {.decision}
**採用:** 認可コードとPKCEを組み合わせ、ブラウザにはセッションCookieのみを保持します。
:::

# 背景

複数のWebアプリケーションで認証方式が分かれており、セキュリティレビューと運用が複雑になっています。認証基盤を共通化し、トークン漏えい時の影響を抑える必要があります。

# 判断基準

- ブラウザ上のトークン露出を最小化できること
- 標準仕様と主要ライブラリで実装できること
- 多要素認証と条件付きアクセスを認証基盤側へ集約できること
- 障害調査に必要な監査ログを取得できること

# 比較した選択肢

| 選択肢 | セキュリティ | 実装負荷 | 運用性 | 判断 |
| --- | --- | --- | --- | --- |
| Authorization Code + PKCE | 高い | 中 | 高い | 採用 |
| Implicit Flow | 低い | 低 | 中 | 不採用 |
| アプリ独自のID・パスワード | 中 | 高 | 低い | 不採用 |

# 影響

アプリケーションは認証基盤へリダイレクトするため、認証基盤の停止がログイン可否へ直接影響します。一方で、認証ポリシーと監査ログは一元化できます。

::: {.warning}
**注意:** セッションCookieには `Secure`、`HttpOnly`、適切な `SameSite` 属性を設定します。
:::

# 見直し条件

- 認証基盤または対応ライブラリのサポート終了
- ブラウザセキュリティモデルの大きな変更
- 外部利用者を含む認証要件への変更
