# 目的

この文書は、Markdownで書いた設計資料をPandocでHTML化するためのサンプルです。本文の読みやすさ、メタ情報、目次、表、コードブロック、注意書きの見え方を確認します。

::: {.note}
**補足:** 記法は[Pandoc User's Guide](https://pandoc.org/MANUAL.html)に従います。fenced divによる注記や表の書き方も同じ資料で確認できます。
:::

# スコープ

対象範囲は次の通りです。

- HTMLとして単体配布できる設計書
- 印刷時にA4で破綻しにくいレイアウト
- 設計判断、未決事項、注意事項を本文内で表現するための最小スタイル

対象外は次の通りです。

- Marpのスライドテーマ
- Docusaurusによるサイト化
- 厳密な版管理ワークフロー

# 前提

| 項目 | 内容 |
| --- | --- |
| 入力 | Pandoc Markdown |
| 出力 | HTML |
| 文字コード | UTF-8 |
| 想定読者 | 開発者、レビュー担当者、運用担当者 |

# 構成

設計書では、背景、要求、方式、インターフェース、データ、運用、リスクを順に記述します。章立てを固定しすぎず、読み手が判断に必要な情報へたどり着きやすい構成を優先します。

::: {.decision}
**決定:** HTMLはCSSを埋め込んだ単体ファイルとして生成します。メール添付やチケット添付で扱いやすくするためです。
:::

# インターフェース

APIやファイル仕様など、読み間違いが起きやすい情報は表で管理します。

| 名前 | 種別 | 必須 | 説明 |
| --- | --- | --- | --- |
| `client_id` | string | yes | 呼び出し元アプリケーションの識別子 |
| `redirect_uri` | URI | yes | 認可後の戻り先 |
| `scope` | string | no | 要求する権限の一覧 |

# エラー処理

代表的なエラーは、発生条件、利用者への影響、復旧方法をセットで記述します。

::: {.warning}
**注意:** 認証失敗時の詳細理由を画面に出しすぎると、攻撃者に手がかりを与える可能性があります。
:::

# 実装メモ

設定例はコードブロックで記述します。

```yaml
auth:
  issuer: "https://id.example.com"
  audience: "example-api"
  token_ttl_minutes: 60
```
